Lesson 20 - Reflection and Annotations

Reflection inspects runtime type metadata, and annotations add machine-readable intent to your code.

1. CLASS MODEL

A class is a blueprint that defines fields, methods, constructors, and modifiers.

  • Compile-time structure
  • Loaded by class loader
  • No dynamic behavior yet
2. REFLECTION

Reflection provides runtime access to class metadata and controlled dynamic invocation.

  • Inspect members
  • Create objects dynamically
  • Invoke methods by metadata
3. ANNOTATION

Annotations mark code with metadata that frameworks and tools read for behavior.

  • Declarative intent
  • Retention can be runtime
  • Drives Spring and JPA workflows
Slide 2

Reflection Fundamentals

Reflection lets Java inspect types at runtime without hard-coding concrete classes.

Core Runtime Types

  • Class<?> for type metadata
  • Field for member variables
  • Method for operations
  • Constructor<?> for creation paths

Where It Is Used

  • Dependency injection and container bootstrapping
  • Object mapping and serialization tools
  • Plugin and module discovery
  • Testing and runtime diagnostics
Class<UserService> type = UserService.class;
String name = type.getSimpleName();
Method[] methods = type.getDeclaredMethods();
System.out.println(name + " has " + methods.length + " methods");
Slide 3

Inspecting Class Metadata

Safe reflection starts with structural inspection before any invocation.

Inspect First

  • Class and package identity
  • Superclass and interfaces
  • Public vs declared members
  • Declared annotations

Common APIs

  • getDeclaredFields()
  • getDeclaredMethods()
  • getConstructors()
  • isAnnotationPresent(...)
Class<Order> type = Order.class;
System.out.println(type.getName());
System.out.println(type.getSuperclass().getSimpleName());
for (Field field : type.getDeclaredFields()) {
    System.out.println(field.getName() + " : " + field.getType().getSimpleName());
}
Slide 4

Working with Fields and Methods

Dynamic invocation is useful, but it should stay explicit and bounded to trusted code.

Field Access Rules

  • Resolve field by exact name
  • Use setAccessible(true) with strict scope
  • Validate expected types before assignment
  • Fail with clear, actionable errors

Method Invocation Rules

  • Resolve exact parameter signature
  • Prepare argument conversion explicitly
  • Handle InvocationTargetException
  • Cache method references in hot paths
User user = new User("Aysel");
Field nameField = User.class.getDeclaredField("name");
nameField.setAccessible(true);
nameField.set(user, "Nigar");

Method greet = User.class.getDeclaredMethod("greet");
String result = (String) greet.invoke(user);
Slide 5

Annotation Basics

Annotations add metadata to code elements and become actionable only through tools, processors, or reflection.

Meta-Annotations

  • @Target controls allowed location
  • @Retention controls lifecycle visibility
  • @Documented adds API docs visibility
  • @Inherited supports class inheritance

Retention Levels

  • SOURCE: compile phase only
  • CLASS: stored in bytecode
  • RUNTIME: accessible via reflection
  • Runtime processing requires RUNTIME
@Target(ElementType.FIELD)
@Retention(RetentionPolicy.RUNTIME)
public @interface NotBlank {
    String message() default "Field cannot be blank";
}
Slide 6

Runtime Annotation Example

Custom validators can scan annotations and enforce constraints without hard-coding per DTO logic.

Validation Flow

  • Read declared fields
  • Check annotation presence
  • Extract runtime value
  • Collect structured violations

Production Notes

  • Keep side effects out of validators
  • Separate scan step from error formatting
  • Cache metadata per class
  • Use tests for null/blank/unsupported types
for (Field field : dto.getClass().getDeclaredFields()) {
    if (!field.isAnnotationPresent(NotBlank.class)) continue;
    field.setAccessible(true);
    Object value = field.get(dto);
    if (value == null || value.toString().trim().isEmpty()) {
        errors.add(field.getName() + " is blank");
    }
}

Framework Use Cases

Spring and JPA combine annotations with reflection to reduce boilerplate and enforce conventions.

Spring Runtime Mapping

  • @Component for bean registration

  • @RequestMapping for endpoint mapping
  • Proxy generation for transactions and AOP

Persistence Mapping

  • @Entity, @Table, @Id
  • Field metadata guides SQL mapping
  • Reflection hydrates result sets into entities
  • Metadata caches improve steady-state speed

Safety and Performance Boundaries

Reflection should be used as infrastructure, not as a default replacement for direct method calls.

Main Risks

  • Encapsulation bypass through private access
  • Runtime failures from signature mismatch
  • Higher overhead in critical loops
  • Security risks on untrusted package scans

Mitigations

  • Allow-list packages and annotations
  • Cache resolved metadata handles
  • Fail fast with deterministic messages
  • Benchmark hot paths with and without reflection
if (!type.getPackageName().startsWith("com.myapp.domain")) {
    throw new SecurityException("Unsupported type: " + type.getName());
}
Method m = methodCache.computeIfAbsent(key, k -> resolveMethod(type, k));
Slide 9

Summary and Checklist

Use reflection and annotations to automate infrastructure behavior while preserving correctness and observability.

Recap

  • Reflection reads metadata at runtime
  • Annotations encode declarative intent
  • Frameworks integrate both for automation
  • Design boundaries prevent fragile code

Implementation Checklist

  • Document every reflection entry point
  • Add tests for missing/invalid annotations
  • Cache metadata for repeated operations
  • Prefer direct code on latency-sensitive paths
Takeaway:
Use direct code first.
Use reflection only when dynamic behavior is required.
Add guardrails, tests, and metrics before production use.
